Resumen

Nexus es una máquina Linux (Ubuntu) larga y encadenada, de las que el nivel «Easy» se le queda muy corto. La web de una eléctrica filtra el correo de un empleado, y un subdominio esconde un Gitea con un repositorio que, en su historial de commits, deja una contraseña y un segundo subdominio: un Krayin CRM.

Con esa contraseña reutilizada entramos al panel de Krayin, que es vulnerable a un RCE autenticado (CVE-2026-38526) y nos da shell como www-data. A partir de ahí, un buen rato de enumeración —con un rabbit hole de base de datos incluido— y reutilización de credenciales para saltar a jones. La escalada a root es lo más jugoso: un timer de systemd que corre como root y ejecuta un script de Python que sincroniza repositorios de Gitea sin sanear las rutas, abriendo un Directory Traversal con el que escribimos nuestra clave SSH en el home de root.

Vulnerabilidad

Nexus no cae por un único fallo, sino por una cadena larga en la que cada eslabón es una mala práctica muy real.

01 · Information Disclosure en el historial de Gitea

El repositorio krayin-docker-setup tiene su .env «limpio» en la rama actual, pero el DB_PASSWORD y un subdominio interno siguen vivos en el historial de commits. Un secreto que se sube y luego se borra sigue ahí: eso es un Information Disclosure de manual.

02 · Reutilización de credenciales

Esa contraseña filtrada no es solo de la base de datos: vale también para el panel del CRM (j.matthew) y, más tarde, para entrar por SSH como jones. La reutilización de credenciales es la que cose toda la máquina.

03 · RCE autenticado en Krayin CRM 2.2.0

El CRM corre una versión vulnerable a un Remote Code Execution autenticado (CVE-2026-38526): con una sesión válida se sube una webshell y se consigue ejecución de comandos como www-data.

04 · Directory Traversal en un servicio de systemd que corre como root

El timer gitea-template-sync.service ejecuta cada minuto, como root, un script que copia los ficheros de los repositorios marcados como plantilla. El script usa el nombre de cada fichero tal cual, sin filtrar los ../, así que un fichero con una ruta trampa (Directory Traversal) se escribe fuera de su carpeta y con permisos de root. Lo aprovechamos para colar una authorized_keys en /root/.ssh/.

Escalada de privilegios

Aquí viene lo bueno, una escalada nueva: abusar de systemd, que para esto funciona como una tarea cron pero con su propio lenguaje. Un .timer marca cuándo se ejecuta algo y un .service marca qué se ejecuta.

Empiezo listando los timers y el servicio que dispara cada uno

Ahora, con un pequeño bucle, miro cuáles corren como root

┌──(jaime㉿kali)-[~]└─$ for s in $(systemctl list-timers --all --no-legend | awk '{print $NF}'); do u=$(systemctl cat "$s" 2>/dev/null | grep -E "^User=" | cut -d= -f2); echo "${u:-root} <- $s"; done

De todos, descarto los estándar del sistema (apt, logrotate, fstrim, sysstat, man-db, fwupd, snapd…), que vienen de paquetes y están bien puestos. El que canta es gitea-template-sync.service.

Lo cateo con systemctl cat, quedándome con lo que importa: ExecStart y User

┌──(jaime㉿kali)-[~]└─$ systemctl cat gitea-template-sync.service | grep -E "ExecStart|User"
User=root ExecStart=/usr/bin/python3 /etc/gitea/template-sync.py

Corre como root y ejecuta un template-sync.py en una ruta rara (lo normal es que apunten a /bin, /usr/bin, /lib/systemd…). El timer lo dispara cada minuto.

A partir de aquí hay cuatro casos posibles; repaso los tres primeros y me quedo con el cuarto.

Caso 1 — el .service es escribible. Si pudiéramos editar el .service, cambiaríamos su ExecStart= por una que nos deje una bash SUID y recargaríamos con systemctl daemon-reload. Compruebo cuáles son escribibles

┌──(jaime㉿kali)-[~]└─$ find /etc/systemd/system /lib/systemd/system -name "*.service" -writable 2>/dev/null

El nuestro no aparece, así que este caso queda descartado.

Caso 2 — el script que ejecuta es escribible. Como una escalada clásica de cron: si el template-sync.py fuese escribible por nosotros, le añadiríamos cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash y a esperar. Tampoco es el caso.

Caso 3 — el directorio del script es escribible. Aunque no podamos tocar el fichero, si tuviéramos permisos sobre su carpeta lo sustituiríamos por uno nuestro. Tampoco.

Caso 4 — leer y entender el script. Nos quedamos con este: leemos el template-sync.py para ver cómo funciona y por dónde romperlo.

Arrancamos por main(), que reparte el trabajo: coge la lista de repos plantilla y manda cada uno a sync_template(), que es donde está la chicha.

Arriba del todo, las rutas con las que trabaja. Las dos que importan: REPO_ROOT = /var/lib/gitea/data/gitea-repositories (de donde lee) y STAGING_DIR = /home/git/template-staging (donde escribe las copias). La gracia va a ser escribir fuera de ese staging.

En get_template_repos() se queda solo con los repos marcados como template. Eso nos pone una condición: nuestro repo tiene que estar como plantilla en Gitea o el script ni lo mira.

Dentro de sync_template() monta dos rutas a partir del dueño y el nombre del repo: el bare de donde lee y el stage_path donde copia.

Lista los ficheros del repo con git ls-tree -r HEAD y guarda de cada uno su filepath tal cual viene del repo, sin limpiar. Eso es justo lo que controlamos.

Y aquí el fallo, en el bucle que escribe cada fichero: target = os.path.join(stage_path, filepath). Como filepath no se filtra, si le metemos ../ o una ruta absoluta, el target se sale del staging y apunta a donde queramos. Y como el script corre como root, el fichero se crea con dueño root.

El plan. Creamos un repositorio en Gitea y lo marcamos como template. Dentro le metemos un fichero cuyo nombre sea la ruta trampa —../../../../../root/.ssh/authorized_keys— y cuyo contenido sea nuestra clave pública SSH. Cuando salte el timer, el script copia ese fichero como root y nos deja la clave en el home de root. No atacamos el contenido del fichero, sino su nombre: eso es el Directory Traversal.

Genero el par de claves (passphrase nexus)

┌──(jaime㉿kali)-[~]└─$ ssh-keygen -t ed25519 -f ./nexus_key

El problema es que Gitea (y git add) rechazan crear un fichero con .. en el nombre.

La solución es montar los objetos de git a mano con plumbing: cuando le das a git el árbol ya construido, no valida los nombres de las entradas. Primero creo un repositorio vacío en Gitea y lo clono

Como hay que anidar varios niveles de .., lo monto con un pequeño script que construye los árboles en crudo con git hash-object y git commit-tree

┌──(jaime㉿kali)-[~]└─$ nano build.sh
#!/bin/bash # blob con la clave publica BLOB=$(git hash-object -w ../nexus_key.pub) # helper: crea un arbol con UNA entrada y devuelve su hash mktree() { { printf '%s %s\0' "$1" "$2"; echo -n "$3" | xxd -r -p; } | git hash-object -t tree -w --stdin --literally; } # de dentro hacia fuera: authorized_keys -> .ssh -> root T=$(mktree 100644 authorized_keys "$BLOB") T=$(mktree 40000 .ssh "$T") T=$(mktree 40000 root "$T") # envolvemos con varios ".." for i in $(seq 1 8); do T=$(mktree 40000 .. "$T"); done # commit, rama y push C=$(git commit-tree "$T" -m x) git update-ref refs/heads/main "$C" git push -f origin main

Ojo con la ruta del nexus_key.pub (yo lo generé fuera del repo) y con ejecutar el build.sh dentro del repositorio clonado. Lo ejecuto y confirmo

Solo queda marcar el repositorio como plantilla (la condición del script) y esperar al timer

Pasado el minuto, me conecto por SSH como root con la clave y su passphrase nexus

Cómo se arregla

La máquina es una cadena de fugas y malas configuraciones; se corta en varios puntos.

  • No subir secretos a git, ni en el historial: el DB_PASSWORD seguía en un commit antiguo. Borrar un secreto no basta: hay que rotarlo y reescribir el historial (o directamente no versionarlo). Es el eslabón que abre toda la máquina.
  • No reutilizar credenciales: la misma contraseña valía para la BD, el CRM y SSH. Con credenciales distintas por servicio, la cadena se rompe en el primer salto.
  • Actualizar Krayin: la 2.2.0 arrastra el CVE-2026-38526. Subir a una versión parcheada elimina el RCE autenticado.
  • No exponer paneles ni Gitea de más: el sitemap.xml regala los usuarios y el repositorio con el .env estaba accesible. Repos sensibles en privado y usuarios no públicos.
  • Sanear rutas en el script de systemd: el fallo de fondo. El template-sync.py debe normalizar cada filepath y rechazar ../ o rutas absolutas antes de escribir, y nunca correr como root si no es imprescindible.
