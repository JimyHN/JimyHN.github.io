Resumen

Dolibarr es distinto al resto del blog: no es una máquina de HackTheBox, es mi Trabajo Fin de Máster de Ciberseguridad. Monté en laboratorio un Dolibarr ERP &amp; CRM 17.0.0 (un ERP/CRM muy usado en pymes) y le hice una auditoría completa de caja gris siguiendo metodología OWASP. Salieron 10 vulnerabilidades, 3 de ellas críticas: dos de ejecución remota de código y un XSS almacenado a través de la API REST. Aquí te resumo el camino a mi estilo; el informe entero (53 páginas, con CVSS, impacto y evidencias) lo tienes enlazado desde el Máster en Títulos.

Vulnerabilidad

CVE-2023-30253 — RCE en el módulo «Sitios Web»

El módulo Sitios Web permite crear páginas con código PHP y, para evitar abusos, filtra la etiqueta de apertura &lt;?php. El problema es que el filtro es sensible a mayúsculas y minúsculas: escribiendo &lt;?pHp se evade por completo, porque al intérprete de PHP le da igual la capitalización. Y como en ese editor no hay lista negra de funciones, system() se ejecuta sin restricción como www-data.

RCE por campos calculados

Los campos calculados se evalúan como PHP. Aquí sí existe una lista negra de funciones peligrosas, pero está incompleta: basta emplear una función que no esté en la lista para ejecutar código (en la prueba devolvió la versión de PHP). Moraleja: las listas negras siempre se quedan cortas.

XSS almacenado vía API REST

El saneamiento de la API REST no cubre los vectores basados en atributos de eventos HTML. Un payload introducido por la API se guarda sin sanear y se ejecuta al visualizar el objeto en la interfaz web: un XSS almacenado cuyo origen es la propia API.

Credenciales de BD en texto plano (el eslabón)

El fichero conf.php guarda la contraseña de MariaDB en claro (la opción de cifrado que ofrece la aplicación está desactivada). Por sí solo ya es grave; combinado con el RCE es demoledor: con ejecución de comandos, se lee el fichero y se accede a toda la base de datos.

Enumeración

Con la cuenta de bajo privilegio reviso cabeceras, componentes y, sobre todo, los módulos activos de la instancia (un escenario típico de pyme): Terceros, Usuarios y grupos, API REST y Sitios Web.

De ahí salen las superficies jugosas:

  • El módulo Sitios Web, que deja crear páginas con PHP.
  • Los campos calculados, que se evalúan como código.
  • La API REST, por donde se crean y modifican objetos de negocio.

También anoto el resto de deficiencias para el informe: sin cifrado en tránsito, política de contraseñas floja, cabeceras y cookies mal configuradas, componentes desactualizados y mensajes de error que filtran versiones.

Explotación

El vector estrella es el módulo Sitios Web. Creo una página y, en el editor, meto el payload con la etiqueta de apertura capada en mayúsculas para esquivar el filtro

<?pHp system('id'); ?>

Guardo la página y solicito su URL pública de renderizado; al servirla, PHP ejecuta el comando

uid=33(www-data) gid=33(www-data) groups=33(www-data)

Ya tenemos ejecución de comandos como www-data.

Los otros dos vectores van en la misma línea: en los campos calculados, una función fuera de la lista negra me devuelve la versión de PHP (RCE confirmada); y por la API REST inyecto un payload en un atributo de evento que termina saltando como XSS almacenado al abrir el objeto en el panel.

Escalada de privilegios

Con ejecución de comandos como www-data, el siguiente paso es claro: leer el fichero de configuración de la aplicación

www-data$ grep dolibarr_main_db_pass /var/www/html/conf/conf.php $dolibarr_main_db_pass='********';

La contraseña de MariaDB está en texto plano (la opción de cifrado estaba desactivada). Con ella entro directamente a la base de datos y me hago con el control total de la información de negocio: terceros, facturas, usuarios...

Esta es la cadena de ataque completa: usuario de pocos privilegios (favorecido por una política de contraseñas floja) → RCE en Sitios Web → comandos como www-data → credenciales del conf.php → base de datos entera. Una vulnerabilidad de severidad media acaba siendo el facilitador de un compromiso crítico.

Cómo se arregla

Casi todo se corrige actualizando Dolibarr (las versiones posteriores arreglan estos fallos), pero conviene verlo por capas:

  • Módulo Sitios Web: no filtrar por cadena literal ni de forma sensible a mayúsculas; lo correcto es no evaluar PHP del usuario o restringirlo con una lista blanca estricta.
  • Campos calculados: las listas negras de funciones siempre se sortean; mejor una lista blanca o directamente un entorno sin ejecución de código.
  • API REST: sanear y escapar la salida también para los atributos de eventos HTML, no solo las etiquetas.
  • conf.php: activar el cifrado de la contraseña de la base de datos y restringir los permisos del fichero.
  • Resto de hallazgos: cifrado en tránsito (TLS), política de contraseñas sólida, cabeceras y cookies de seguridad, actualización de componentes y mensajes de error genéricos.

Conclusiones

Dolibarr 17.0.0 demuestra algo que se repite en auditorías reales: un solo fallo de validación (un filtro sensible a mayúsculas) basta para pasar de un usuario normal a ejecución de comandos, y de ahí, tirando del conf.php, al control total del sistema.

También deja una idea muy clara: las listas negras (de etiquetas o de funciones) son un parche que siempre se puede esquivar, frente a las listas blancas, que deniegan por defecto.

Y lo más importante: casi todos los fallos están corregidos en versiones posteriores, así que la mejor defensa sigue siendo mantener el software actualizado.
